# 第三关开始卡顿：排查记录

反馈条件：微信内打开，第三关一开始就卡；手机型号未知。

本次只排查，没有修改游戏源码、玩法、画质或分辨率配置，没有编译或发布。新增文件为本地诊断脚本、截图和测量记录。

## 结论

最有证据支持的方向是第三关泡泡数量骤增，放大了每帧全量更新和网格重建的开销。即使停在开始发射前的 Ready 状态，这些开销也持续存在。它与“第三关一开始就卡”的反馈吻合，但尚未取得反馈手机的性能记录，不能把桌面数据当成微信手机上的实测帧率。

当前证据不支持优先把原因归为连续切关后的资源累积，也不能据此完全排除泄漏。

## 可复查的测试

运行本地现有 WebGL 产物；全新、隔离的 Chrome 测试配置；A 关卡集；390×844 CSS 视口、DPR 2，对应实际画布 780×1688；等待进场完成，在 Ready 状态采样 12 秒。两关均由独立页面导航直接进入，没有要求先玩完前两关。

纠正 WebGL2 上传范围计数后复测：

| 指标 | 第二关 | 第三关 |
| --- | ---: | ---: |
| 实际可见泡泡 | 258 | 3600 |
| 浏览器主线程任务时间／显示帧 | 2.15 ms | 5.23 ms |
| WebGL 索引数量／帧（约） | 6027 | 46238 |
| WebGL drawElements 调用／帧（约） | 9 | 9 |
| bufferData / bufferSubData 提交字节／帧（约） | 0.181 MiB | 1.475 MiB |
| rAF 帧率 | 60 | 60 |

两次普通速度对比都出现第三关负载明显升高：第一轮主线程任务时间为 2.79 → 5.39 ms，复测为 2.15 → 5.23 ms。桌面没有稳定复现明显掉帧，因此这里确认的是负载跃升，不是反馈设备的掉帧幅度。

首轮还做了 Chrome 4 倍 CPU 降速诊断：第三关约 15.9 ms／帧，已接近 60 fps 的 16.7 ms 时间预算。仅在该隔离测试浏览器中将 DPR 2 改为 DPR 1，仍约 16.0 ms／帧，没有缓解主线程负担。该实验未修改游戏配置，也不能等同于真实低端手机。后续优化应先处理 CPU 重复工作，无需以降画质或分辨率为前提。

原始记录：`browser/result.json`、`browser-verified/result.json`。首轮上传计数误把 WASM 整体内存视图当作上传范围，错误字段已移除，并在原始记录中注明；上传字节以复测为准。跨页面导航记录的 JS heap 数值不能作为游戏泄漏证据。采样文件 `*.cpuprofile` 的 WASM 函数名已剥离，因此不声称已测得下列各个 C# 方法独立的耗时占比。
