## 3. 规则（第一版）

### 3.1 两种生成模式

B 套每关必须属于下列两种模式之一，并在关卡文件旁的清单 `manifest.json` 里登记所用模式。

**模式 S：严格保留**

B 关与 A 关相比，**只允许 `cells` 的排布和 `title` 不同**，其余字段逐字段完全相同：

- 全部参数；
- `queue` 全部字段；
- `stream`、`streamOffsets`；
- `palette`。

由此推出：棋盘上每种颜色的格子数与 A 关相同。

**模式 P：整体颜色置换**

允许一个**颜色索引置换 σ**，例如原来蓝色当背景，新图改用橙色当背景。条件：

- σ 是双射，并且只在该关**已出现的颜色索引之间**置换，颜色集合不变，所以初次登场表仍然有效。
- σ **同时作用于**以下三处：
  - `cells`；
  - `stream`；
  - `queue[].color`。

  `queue[].other` **不置换**：实施时核对，它只出现在特殊队员（kind 3/4）上，取值为 5/10/15/20，是数值参数而不是颜色索引。

  等价于整关换色，各色弹量守恒自动成立。
- `palette` 不变（σ 改的是索引的使用，不改索引对应的 RGB）。
- σ 记录在清单里。

**校验方法**：

- 模式 S：B 与 A 直接逐字段比较，只排除 `cells` 和 `title`。
- 模式 P：先对 B 的 `cells`、`stream`、`queue` 施加 σ⁻¹，**还原颜色编号**，再与 A 逐字段比较，同样只排除 `cells` 和 `title`。
- 两种模式都额外检查：
  - 棋盘各色格子数与 A 关一致（模式 P 先还原再比）；
  - 各色弹量守恒。

### 3.2 格子数补齐（工具自动完成）

画图的人只需按参考比例画。转换工具量化后，若某色格子数与目标不一致，就在**颜色交界处**做最小改动补齐：

- 多出的边缘格改成相邻的缺额颜色；
- 缺少的颜色从相邻多余颜色的边缘借。

**目标是 0 偏差**，补齐后格子数必须与目标完全一致；预览图要标出被改动的格子。

补齐改动量超过阈值时（初值：任一颜色改动超过其目标格数的 10%（小色块至少允许 4 格），或总改动超过 120 格 ≈ 3.3%），工具报"需要重画或换置换方案"，不自动接受。

### 3.3 第一版不做的事

- **不改沙流、不改弹量**。原计划的 R4 例外通道移到附录 A，作为后续选项。
- **不改** `palette`、参数、队员。

## 4. 实施步骤

### 第 1 步：定口径（已完成）

即第 3 节规则与第 5 节进度方案。剩余待定项见第 7 节。

### 第 2 步：转换工具 `scripts/levels_b/`（预计 1–2 天）

> 进度（10-19）：配色表、转换、校验、预览、临时图、自测已完成，用法见 `scripts/levels_b/README.md`。`publish.py`、`stage_test.py` 随第 3 步接入一起做。

**输入**：一张图（任意尺寸 PNG）、游戏关号（第 3 到 262 关），以及可选的置换 σ。

**输出**：B 关 json、清单条目、预览图。

**存放位置与发布状态**（P2-3）：

- 草稿区：`Art/levels-b/work/`，在资源目录之外，**游戏读不到**。工具默认输出到这里，包括所有临时图、翻转图。
- 清单：`Art/levels-b/manifest.json`。每关一条，记录：
  - 游戏关号、资源名、模式（S / P）、置换 σ、源图路径与哈希；
  - B 关的 `fileSha256` 和 `cellsSha256`（口径见下）；
  - 评估结论、人工结论；
  - 状态：`draft`（草稿）→ `evaluated`（已评估）→ `approved`（已验收、允许发布）。
- 发布：`scripts/levels_b/publish.py` 只把 `approved` 的关复制到 `Resources/levels/B/`，同时生成运行时清单 `Resources/levels/B/released.json`。清单逐关记录：游戏关号、资源名、`fileSha256`、`cellsSha256`。

**两种哈希的口径**（P2-1）：

| 名称 | 计算对象 | 用途 |
|---|---|---|
| `fileSha256` | 关卡 json 文件的原始字节（运行时为 `TextAsset.bytes`） | 校验发布的文件就是验收过的那份：构建前检查、进关时校验 |
| `cellsSha256` | `cells` 数组，规范编码为十进制整数用英文逗号连接、无空格、UTF-8，例如 `3,3,10,...` | 核对实际加载的棋盘：运行时对 `JsonUtility` 解析出的 `LevelData.cells` 按同一编码计算 |

Python 工具和 C# 运行时使用同一编码，工具附带一组固定样例，两边结果必须一致。

1. **配色表导出**：对每关列出：
   - 可用颜色：RGB、对应队员名、颜色索引；
   - 各色目标格数和占比；
   - 允许的置换（该关已出现的颜色）。

   汇总成全关配色总表，供挑题材、写提示词用。
2. **量化**：缩放到 60 × 60，用最近色映射到该关可用颜色（像素画默认不抖动），并按 σ 处理。
3. **补齐**：按 3.2。
4. **校验**：按 3.1，任一不通过就报错。另外检查：
   - 尺寸为 60 × 60；
   - 颜色索引合法；
   - `streamOffsets` 长度为 61、末项等于沙流长度（与 `Battle.Construction` 的构造检查一致）。
5. **预览**：
   - 泡泡皮肤配色的棋盘图，标出补齐改动的格子；
   - A/B 并排对比图；
   - 文件名带关号，例如 `第003关_sector01.png`。

**临时图**：开发阶段用 A 套原图左右翻转（模式 S，格子数天然相等）和"原图加置换"（模式 P）生成临时 B 关卡，不依赖最终图案。

**验收**：
- 临时图能转出合法关卡；
- 编辑器批处理里用 B 关 json 构造 `Battle` 不报错；
- 故意篡改一处队员字段时，校验能拦截。

### 第 3 步：游戏接入骨架（用临时 B 关卡，预计 1–2 天）

**目标**：在投入图案生产之前，先跑通切换、保存、回退。

**加载方案：不改任何受保护文件**

1. **B 关放置**：`Resources/levels/B/sectorNN.json`，全部是新文件，不在保护清单里。这个目录**只放已验收的关**，由 `publish.py` 写入。
2. **切换方式**：`Levels` 是 `static readonly string[]`，只读的是引用，数组元素可以改。泡泡层（`#if FLIGHTBEAT_GARDEN_R1 || UNITY_EDITOR`，放在 `Garden/` 下的新文件）提供 `ApplyLevelSet(set)`：
   - 启动时保存一份 A 套原名的副本；
   - **按 `released.json` 启用，不按文件是否存在**：只有列入清单、并且文件能读到的关，才把 `Levels[i]` 改成 `"B/sectorNN"`；其余**保留 A 名**，实现逐关回退；
   - 切回 A 时，从副本全部恢复为原名。
3. **生效时机**：加载点 `ResetRuntime()` 不需要改动，下次进关时自然读到新名字。
4. **调用时机**：
   - 启动时（读取保存的选择）；
   - 设置里切换时：只更新选择和数组，**当前对局不受影响，下次进关生效**。
5. **两类检查分开**（P1-2）：
   - **原版回归（固定 A）**：
     - 包括 `check_source.py`、现有回归证据、`BubbleMigrationChecks` 的默认运行；
     - 不调用 `ApplyLevelSet`，`Levels` 保持原名；
     - 运行前断言 `Levels` 与原名逐项相同，不同就直接失败。
   - **B 套验收（显式指定 B）**：
     - 通过参数 `--level-set B` 启动，例如在 `check_levels.sh` 和打关评估里各加一个参数；
     - 运行前调用 `ApplyLevelSet(B)`，`finally` 里一定恢复 A 名，避免影响同进程后续检查；
     - **核对实际加载内容**：每关进关后记录当前 `Levels[i]`、加载文件的 `fileSha256`、解析后棋盘的 `cellsSha256`，分别与 `released.json`（测试时为 `test.json`）中对应字段比对；两项都一致才算"实际来源：B"；
     - 报告逐关写"实际来源：B / 回退 A"。**回退 A 的关不计入 B 套通过数**，单独列出。
   - 构建前检查（`build.sh` 增加一步）：
     - `Resources/levels/B/` 下每个文件都必须在 `released.json` 里、`fileSha256` 一致，并在 `manifest.json` 里为 `approved`；
     - 有多余或未验收的文件，就构建失败；
     - `Resources/levels/B-test/` 存在时，正式构建失败（见下方"临时关卡测试通道"）。

**临时关卡测试通道**（P2-2）：

本步要用临时 B 关卡（翻转图等）验证接入，它们**不能标成 `approved`**，所以单独走测试通道：

1. **放入**：`scripts/levels_b/stage_test.py <关号...>` 从草稿区把指定临时关复制到 `Resources/levels/B-test/`，生成 `Resources/levels/B-test/test.json`。格式同 `released.json`，每条加 `"status": "test"`。
2. **运行时**：`ApplyLevelSet(B)` 先按 `released.json` 启用正式 B 关，再**仅当 `test.json` 存在时**，用测试关覆盖对应关号，名字为 `"B-test/sectorNN"`。报告和调试信息里来源写"B-test"，不计入正式 B 套通过数。
3. **构建**：
   - `build.sh` 默认是正式构建，发现 `Resources/levels/B-test/` 就失败；
   - 测试构建需要显式设置 `R1_LEVELS_TEST=1`，产物标记为测试版；
   - 发布流程拒绝发布测试版产物。
4. **清除**：测试结束运行 `stage_test.py --clean`，删除 `B-test/` 目录及其 `.meta`。`git` 也忽略这个目录（加入 `.gitignore`），防止误提交。

### 第 4 步：难度评估（预计 3–4 天，关键）

现有的 `scripts/r1v3/check_levels.sh` 和 `BubbleMigrationChecks` **只验证进关和首次出战**，不验证通关。所以需要新写一个**完整打关的自动评估**。

**运行环境**：

- 编辑器批处理，直接构造 `Battle`（参照 `Editor/LegacyModelStage.cs` 的 `New(level)`）。模型是确定性的（有 `seed`）。
- B 关 json 直接从文件读入构造，**不经过 `Levels` 数组**，不影响原版回归。
- **固定条件**，A、B 两套完全相同：
  - 成长配置：使用 `New(level)` 的默认配置，不加科技、核心或装备加成；
  - 道具：不用道具（不调用 `Designate`、`Shuffle`、`LaunchSuperStrike`）。

**运行规则**（P1-1，与游戏一致）：

1. **步长**：每步调用 `Battle.Tick(0.02f)`，与 `Game/PixelWingGame.Frame.cs:110` 的固定步长一致。不模拟顿帧和慢放，那些只影响画面时钟。
2. **开场**：`Intro` 阶段只推进、不操作；进入 `Ready` 或 `Playing` 后开始决策。
3. **决策**：每 0.6 秒（30 步）做一次决策，最多上阵 1 名队员。
   - 调用 `Deploy(lane)`；返回 `false`（上阵位满等）视为本次不操作；
   - 策略**没有候选**时（没有可上阵的列，或上阵位已满）不操作，继续推进，等下一次决策。
4. **复活**：状态为 `ReviveOffer` 时，继续 `Tick` 不会推进，所以要**立即调用 `DeclineRevive()`**，记为失败。这与游戏内自动打关（`Frame.cs` 的 autoplay 分支）的做法一致。
5. **终局决战**：每一步检查 `FinaleReady`（队列已空、场上有队员、剩余 1–999 等）。一旦为真就**立即** `LaunchFinale(mode)`，`mode` 用默认成长配置下 `Finale.ModeFor` 的结果，两套相同。报告里记录发动时刻。
6. **结束条件**：
   - 状态变为 `Won` 或 `Lost` 时结束；
   - **最长模拟 900 秒**（45 000 步），超时就结束，结果记为"超时"，按"无法判断"处理；
   - 另设**无进展保护**：连续 120 秒 `Remaining` 不变且无上阵，提前结束，同样记为"超时"。

**策略**（各自独立跑一遍）：

0. **内置建议（基准）**：每次决策上阵 `Battle.SuggestedQueue()` 给出的列。这就是游戏自带自动打关用的规则，用作对照。
1. **优先攻击**：优先上阵当前暴露颜色可命中的队员，多个可选时选子弹最多的。
2. **优先合成**：优先选上阵后**能凑成三合一**的队员；没有就退回策略 1。判断条件（评估脚本自写，**不调用原模型的 `WouldMerge()`**，它会排除问号队员）：
   - 有空上阵位：`Fleet.Count < UnlockedSlots`；
   - 设该列队首队员的颜色为 c，**问号队员（`Kind == 2`）按其真实颜色 `Color` 计算**，因为队首会揭示颜色、上阵后照常参与合成；
   - 场上颜色为 c 的队员数 k 满足 `k % 3 == 2`，即再上一名就凑够 3 个。只有 1 名同色时不算，与模型合成规则 `Merge()`（同色、到位后满 3 个就合）一致，和泡泡层已修正的「合」提示 `GardenMergeHintVisible` 口径相同。

   注：策略 0 直接用 `SuggestedQueue()`，保持游戏原样，不受此规则影响。
3. **优先清位**：优先保持上阵位有空，选子弹少、能尽快打完离场的队员；没有就退回策略 1。

候选相同时，按列号从小到大取第一个，保证结果可复现。

**指标**（逐关 × 策略，输出 A 值、B 值、差值）：

- 胜负；
- 用时；
- 卡住总时长（上阵队员都打不到目标的时间）；
- 前排离护栏的最近距离；
- 换人次数、合成次数；
- 各色首次暴露时间。

**判定**（逐关 × 策略）：

| A 结果 | B 结果 | 判定 |
|---|---|---|
| 胜 | 胜 | 比较用时、卡住时长、最近距离，均在容差内为"通过"，否则"超差" |
| 胜 | 负 | **超差** |
| 负 | 胜 | **超差** |
| 负 | 负 | **无法判断**，转人工试玩 |
| 任一方超时 | — | **无法判断**，转人工试玩 |

- 容差初值：用时与卡住时长 ±10%，最近距离 ±3 px。试点后用人工试玩校准。
- 一关**四种策略全部通过**才算通过；任一超差就回去改图案或换置换方案；有"无法判断"的必须人工试玩。

**验收**：
- A 套与自身比较时差值全为 0（验证确定性与评估脚本）；
- 临时 B 关卡（翻转图）能产出完整报告。

## 附录 A：例外通道（后续选项，第一版不实施）

适用场景：某色在图案里确实需要与目标明显不同的数量，补齐会破坏画面。

- **偏差定义**：对每种颜色 c，设棋盘目标格数为 T(c)、新图格数为 B(c)，偏差为 |B(c) − T(c)|。
- **上限**：每种颜色偏差 ≤ max(10% × T(c), 20 格)，并且 Σ|B(c) − T(c)| / 2 ≤ 3600 的 5%。超出就重画。
- **首选做法：用沙流吸收，弹量不变**。
  - 沙流是按列分别补入的，**不能取整个 `stream` 数组的末尾**；
  - 应在各列队尾（第 c 列的 `stream[streamOffsets[c+1]-1]` 往前）改色，把差额分摊到多列，每列改动尽量少；
  - 改色后各色"棋盘 + 沙流"仍等于该色弹量。
- **限制**：
  - 第 3 关（`sector01`）没有沙流，不能用；
  - 某列沙流不足时，分摊到其他列。
- **备选做法**：按比例缩放该色队员子弹，用最大余数法取整，队员数量、顺序、列不变。会改变换人节奏，难度风险更高。
- **校验**：需要在第 3.1 节外新增"模式 E"，写明允许改动的字段与范围。
- **复核**：走例外通道的关**必须**四策略评估加人工试玩，并重新检查沙流改色对各列遮挡与暴露顺序的影响。
- 10-22 18:30 用户：命中像碎成渣渣，不像泡泡破。爆破改为肥皂泡「啵」：0.05 秒鼓到 1.3 倍并软抖后消失，一圈泡泡同色调浅色细环快速张开淡出，稀疏命中加 4 条短「啵」爆线，3–5 颗半透明雾点外飘淡出（无重力）；去掉弧形碎膜和会下落的实心小球；总时长 0.42 → 0.22 秒。
