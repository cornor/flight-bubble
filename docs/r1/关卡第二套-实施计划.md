## 3. 规则（第一版）

### 3.1 两种生成模式

B 套每关必须属于下列两种模式之一，并在关卡文件旁的清单 `manifest.json` 里登记所用模式。

**模式 S：严格保留**

B 关与 A 关相比，**只允许 `cells` 的排布和 `title` 不同**，其余字段逐字段完全相同：

- 全部参数；
- `queue` 全部字段；
- `stream`、`streamOffsets`；
- `palette`。

由此推出：棋盘上每种颜色的格子数与 A 关相同。

**模式 P：整体颜色置换**

允许一个**颜色索引置换 σ**，例如原来蓝色当背景，新图改用橙色当背景。条件：

- σ 是双射，并且只在该关**已出现的颜色索引之间**置换，颜色集合不变，所以初次登场表仍然有效。
- σ **同时作用于**以下三处：
  - `cells`；
  - `stream`；
  - `queue[].color`。

  `queue[].other` **不置换**：实施时核对，它只出现在特殊队员（kind 3/4）上，取值为 5/10/15/20，是数值参数而不是颜色索引。

  等价于整关换色，各色弹量守恒自动成立。
- `palette` 不变（σ 改的是索引的使用，不改索引对应的 RGB）。
- σ 记录在清单里。

**校验方法**：

- 模式 S：B 与 A 直接逐字段比较，只排除 `cells` 和 `title`。
- 模式 P：先对 B 的 `cells`、`stream`、`queue` 施加 σ⁻¹，**还原颜色编号**，再与 A 逐字段比较，同样只排除 `cells` 和 `title`。
- 两种模式都额外检查：
  - 棋盘各色格子数与 A 关一致（模式 P 先还原再比）；
  - 各色弹量守恒。

### 3.2 格子数补齐（工具自动完成）

画图的人只需按参考比例画。转换工具量化后，若某色格子数与目标不一致，就在**颜色交界处**做最小改动补齐：

- 多出的边缘格改成相邻的缺额颜色；
- 缺少的颜色从相邻多余颜色的边缘借。

**目标是 0 偏差**，补齐后格子数必须与目标完全一致；预览图要标出被改动的格子。

补齐改动量超过阈值时（初值：任一颜色改动超过其目标格数的 10%（小色块至少允许 4 格），或总改动超过 120 格 ≈ 3.3%），工具报"需要重画或换置换方案"，不自动接受。

### 3.3 第一版不做的事

- **不改沙流、不改弹量**。原计划的 R4 例外通道移到附录 A，作为后续选项。
- **不改** `palette`、参数、队员。

**输入**：一张图（任意尺寸 PNG）、游戏关号（第 3 到 262 关），以及可选的置换 σ。

**输出**：B 关 json、清单条目、预览图。

**存放位置与发布状态**（P2-3）：

- 草稿区：`Art/levels-b/work/`，在资源目录之外，**游戏读不到**。工具默认输出到这里，包括所有临时图、翻转图。
- 清单：`Art/levels-b/manifest.json`。每关一条，记录：
  - 游戏关号、资源名、模式（S / P）、置换 σ、源图路径与哈希；
  - B 关的 `fileSha256` 和 `cellsSha256`（口径见下）；
  - 评估结论、人工结论；
  - 状态：`draft`（草稿）→ `evaluated`（已评估）→ `approved`（已验收、允许发布）。
- 发布：`scripts/levels_b/publish.py` 只把 `approved` 的关复制到 `Resources/levels/B/`，同时生成运行时清单 `Resources/levels/B/released.json`。清单逐关记录：游戏关号、资源名、`fileSha256`、`cellsSha256`。

**两种哈希的口径**（P2-1）：

| 名称 | 计算对象 | 用途 |
|---|---|---|
| `fileSha256` | 关卡 json 文件的原始字节（运行时为 `TextAsset.bytes`） | 校验发布的文件就是验收过的那份：构建前检查、进关时校验 |
| `cellsSha256` | `cells` 数组，规范编码为十进制整数用英文逗号连接、无空格、UTF-8，例如 `3,3,10,...` | 核对实际加载的棋盘：运行时对 `JsonUtility` 解析出的 `LevelData.cells` 按同一编码计算 |

Python 工具和 C# 运行时使用同一编码，工具附带一组固定样例，两边结果必须一致。

1. **配色表导出**：对每关列出：
   - 可用颜色：RGB、对应队员名、颜色索引；
   - 各色目标格数和占比；
   - 允许的置换（该关已出现的颜色）。

   汇总成全关配色总表，供挑题材、写提示词用。
2. **量化**：缩放到 60 × 60，用最近色映射到该关可用颜色（像素画默认不抖动），并按 σ 处理。
3. **补齐**：按 3.2。
4. **校验**：按 3.1，任一不通过就报错。另外检查：
   - 尺寸为 60 × 60；
   - 颜色索引合法；
   - `streamOffsets` 长度为 61、末项等于沙流长度（与 `Battle.Construction` 的构造检查一致）。
5. **预览**：
   - 泡泡皮肤配色的棋盘图，标出补齐改动的格子；
   - A/B 并排对比图；
   - 文件名带关号，例如 `第003关_sector01.png`。

**临时图**：开发阶段用 A 套原图左右翻转（模式 S，格子数天然相等）和"原图加置换"（模式 P）生成临时 B 关卡，不依赖最终图案。

**运行规则**（P1-1，与游戏一致）：

1. **步长**：每步调用 `Battle.Tick(0.02f)`，与 `Game/PixelWingGame.Frame.cs:110` 的固定步长一致。不模拟顿帧和慢放，那些只影响画面时钟。
2. **开场**：`Intro` 阶段只推进、不操作；进入 `Ready` 或 `Playing` 后开始决策。
3. **决策**：前两轮固定每 0.6 秒决策；第三轮改为每种打法默认跑 12 次，种子为 1–12，每次决策间隔在 0.4–0.8 秒随机，并有 15% 的概率跳过本次操作，最多上阵 1 名队员。同等候选加入随机选择。
   - 调用 `Deploy(lane)`；返回 `false`（上阵位满等）视为本次不操作；
   - 策略**没有候选**时（没有可上阵的列，或上阵位已满）不操作，继续推进，等下一次决策。
   - `--self` 与正式 A/B 使用相同种子；`--noise` 两边都用 A 原关，分别使用 1–12 与 1001–1012，测量当前机器人的采样波动。
   - 这些随机操作参数是评估模型的设定，尚未通过真人操作数据校准。
4. **复活**：状态为 `ReviveOffer` 时，取用每局唯一一次 `Revive()`，记录是否使用和发动时刻；已经复活或复活失败才调用 `DeclineRevive()`。A、B 使用相同规则。此规则自第二轮起生效，首轮证据仍是拒绝复活的旧规则。
5. **终局决战**：每一步检查 `FinaleReady`（队列已空、场上有队员、剩余 1–999 等）。一旦为真就**立即** `LaunchFinale(mode)`，`mode` 用默认成长配置下 `Finale.ModeFor` 的结果，两套相同。报告里记录发动时刻。
6. **结束条件**：
   - 状态变为 `Won` 或 `Lost` 时结束；
   - **最长模拟 900 秒**（45 000 步），超时就结束，结果记为"超时"，按"无法判断"处理；
   - 另设**无进展保护**：连续 120 秒 `Remaining` 不变且无上阵，提前结束，同样记为"超时"。

**策略**（前两轮各跑一遍，第三轮起各跑 12 次）：

0. **内置建议（基准）**：每次决策上阵 `Battle.SuggestedQueue()` 给出的列。这就是游戏自带自动打关用的规则，用作对照。
1. **优先攻击**：优先上阵当前暴露颜色可命中的队员，多个可选时选子弹最多的。
2. **优先合成**：优先选上阵后**能凑成三合一**的队员；没有就退回策略 1。判断条件（评估脚本自写，**不调用原模型的 `WouldMerge()`**，它会排除问号队员）：
   - 有空上阵位：`Fleet.Count < UnlockedSlots`；
   - 设该列队首队员的颜色为 c，**问号队员（`Kind == 2`）按其真实颜色 `Color` 计算**，因为队首会揭示颜色、上阵后照常参与合成；
   - 场上颜色为 c 的队员数 k 满足 `k % 3 == 2`，即再上一名就凑够 3 个。只有 1 名同色时不算，与模型合成规则 `Merge()`（同色、到位后满 3 个就合）一致，和泡泡层已修正的「合」提示 `GardenMergeHintVisible` 口径相同。

   注：策略 0 直接用 `SuggestedQueue()`，保持游戏原样，不受此规则影响。
3. **优先清位**：优先保持上阵位有空，选子弹少、能尽快打完离场的队员；没有就退回策略 1。

策略 1–3 增加防堵位：只剩最后一个空位时，仅允许能凑成三合一，或该颜色在至少 3 列前排暴露的队员上阵；多个候选取弹量最多的。策略 0 继续直接使用游戏内置建议。第三轮中，策略 1–3 的同等候选用固定种子的随机数选择；当前实现对每个后续同优候选以 50% 概率替换，存在列号偏差（3 个候选概率为 25%、25%、50%），待修正为均匀选择。

## 5. 进度方案（第一版：共用进度）

- 两套**共用** `FleetProfile` 的全部进度：`unlocked`、`cleared`、连胜、每日数据、战区奖励、图鉴、"重置进度"。
- **关号是共同键**：在 A 套通过第 N 关，B 套第 N 关也视为已通过，反之亦然。由于两套同号关难度一致，这样处理合理。
- **结算归属**：对局按"进关时"的关卡套运行，结算照常写入共用进度，不区分套。
- **体验新图案**：通过第 3 步的"选关 / 重玩"入口，已解锁的关都能用当前所选的套重玩；结算沿用原版首通与重玩规则（`FleetEconomy.Reward.cs` 的 `first`）。
- **切换时机**：只在下次进关生效。未结算对局（`attempt`、`attemptLevel`）保持原样。中途退出后再进，按当时选择的套加载；同号关难度一致，不影响结算。
- **图鉴**：仍按 `cleared` 判断，不受切换影响。

**独立进度（后续议题，第一版不做）**。若以后需要，至少要先解决：

1. 图鉴获得改为独立的"已获得伙伴"记录，与各套 `cleared` 解耦，避免切套后锁掉已得伙伴；
2. 两套各自的 `unlocked`、`cleared` 存在泡泡层独立键里，切换时换入换出；
3. 未结算对局的归属：记录开局时的套，只在同套结算；
4. 战区奖励、每日任务、连胜、"重置进度"按套还是全局，需要逐项定义。

## 附录 A：例外通道（后续选项，第一版不实施）

适用场景：某色在图案里确实需要与目标明显不同的数量，补齐会破坏画面。

- **偏差定义**：对每种颜色 c，设棋盘目标格数为 T(c)、新图格数为 B(c)，偏差为 |B(c) − T(c)|。
- **上限**：每种颜色偏差 ≤ max(10% × T(c), 20 格)，并且 Σ|B(c) − T(c)| / 2 ≤ 3600 的 5%。超出就重画。
- **首选做法：用沙流吸收，弹量不变**。
  - 沙流是按列分别补入的，**不能取整个 `stream` 数组的末尾**；
  - 应在各列队尾（第 c 列的 `stream[streamOffsets[c+1]-1]` 往前）改色，把差额分摊到多列，每列改动尽量少；
  - 改色后各色"棋盘 + 沙流"仍等于该色弹量。
- **限制**：
  - 第 3 关（`sector01`）没有沙流，不能用；
  - 某列沙流不足时，分摊到其他列。
- **备选做法**：按比例缩放该色队员子弹，用最大余数法取整，队员数量、顺序、列不变。会改变换人节奏，难度风险更高。
- **校验**：需要在第 3.1 节外新增"模式 E"，写明允许改动的字段与范围。
- **复核**：走例外通道的关**必须**四策略评估加人工试玩，并重新检查沙流改色对各列遮挡与暴露顺序的影响。
